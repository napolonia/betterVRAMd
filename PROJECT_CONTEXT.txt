betterVRAMd — PROJECT CONTEXT / HANDOVER

Last updated: 2026-11-26

1. PROJECT OBJECTIVE

Build betterVRAMd, a self-contained Linux/WSL2 VRAM manager that manages its own inference workloads.

Core objective:

Keep model files/pages available in system RAM when practical.
Keep model-owned VRAM allocations at zero while idle.
Allocate GPU resources only when inference is requested.
Release GPU resources immediately after inference.
Verify actual GPU memory reclamation.
Support CPU-only, hybrid CPU/GPU and full GPU inference.
Support multiple registered GGUF models.
Use separate inference worker processes.
Prioritize reliability and resource safety over inference speed.

Phase 1 is Linux/WSL2 only.

Out of scope for Phase 1:

Windows companion service.
ComfyUI integration.
GUI.
Windows integration.

4. RESOURCE SAFETY

The machine freezes when inference runs alongside Chrome, VS Code and WSL2.

Chrome must remain available because it is being used to communicate with ChatGPT.

Development strategy:

Build the complete Phase 1 system before integrated inference testing.
Avoid unnecessary GPU workloads.
Do not indiscriminately pin model pages using mlock.
Do not introduce concurrent inference workers.
Keep resource limits configurable.
Prioritize CPU and RAM safety as well as VRAM safety.

Initial GPU configuration:

Total VRAM: 4096 MiB
Initial VRAMd budget: 1800 MiB
Minimum desired free VRAM: 512 MiB
Automatic budgeting enabled
Maximum inference workers: 1

These are conservative initial limits, not guaranteed allocation amounts.

RAM:

Maximum configured application budget: 4096 MiB
System reserve: 2048 MiB
Memory locking disabled
Default cache strategy: mmap

Important distinction:

Filesystem page cache
Explicitly pinned RAM
Memory-mapped model files
VRAM allocations

These are separate concepts and must remain separate in the architecture.

Responsibilities:

Read-only system and GPU measurements.
Never allocate memory.

CORE:

Resource budgeting.
Scheduling.
Allocation decisions.
Lifecycle coordination.

MODEL CACHE:

Memory mapping.
Optional page warming.
Cache tracking.
No indiscriminate memory locking.

WORKER:

Execute inference.
Own backend resources.
Terminate after inference to reclaim GPU allocations.

REGISTRY:

Track model identity, location and metadata.
Never load model weights.

MANAGER:

Coordinate component startup and shutdown.
Own component lifecycle.
Expose application status.
