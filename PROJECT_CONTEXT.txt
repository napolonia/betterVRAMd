Last updated: 2026-11-26


1. PROJECT OBJECTIVE

Build betterVRAMd, a self-contained Linux/WSL2 VRAM manager that manages its own inference workloads.

Core objective:

Keep model files/pages available in system RAM when practical.
Keep model-owned VRAM allocations at zero when no model is resident.
Allocate GPU resources when a model is loaded for inference.
Keep loaded models available across multiple inference requests.
Release GPU resources when models are unloaded or evicted.
Verify actual GPU memory reclamation.
Support CPU-only, hybrid CPU/GPU and full GPU inference.
Support multiple registered GGUF models.
Use separate inference worker processes.
Prioritize reliability and resource safety over inference speed.

Model residency and inference activity are separate states.
An idle inference queue does not necessarily mean the loaded model must be unloaded.
Model unloading is controlled by the LifecycleController and resource-management policy.

4. RESOURCE SAFETY

The machine freezes when inference runs alongside Chrome, VS Code and WSL2.

Chrome must remain available because it is being used to communicate with ChatGPT.

Development strategy:

Build the complete Phase 1 system before integrated inference testing.
Avoid unnecessary GPU workloads.
Do not indiscriminately pin model pages using mlock.
Do not introduce concurrent inference workers.
Keep resource limits configurable.
Prioritize CPU and RAM safety as well as VRAM safety.

Responsibilities:

INFERENCE BACKEND ARCHITECTURE

Primary backend: llama.cpp using llama-server.

llama-server provides persistent model residency and
HTTP-based inference.

The server remains running while its model is resident.
Multiple inference requests use the same loaded model
without reloading weights.

Backend responsibilities:

base.py:
Defines the backend-independent inference interface.
Defines common result types and exception classes.
Does not contain llama.cpp-specific implementation.

llama_cpp.py:
Implements the primary llama-server backend.
Validates the configured executable and model path.
Builds the llama-server command.
Provides HTTP readiness and inference interfaces.
Does not create or terminate the server process.

llama_cli.py:
Future optional backend.
Not part of the initial implementation.

PROCESS OWNERSHIP

worker/process.py owns the llama-server subprocess lifecycle.

Responsibilities:
- Process creation.
- Process tracking.
- Startup readiness monitoring.
- Graceful shutdown.
- Forced termination when configured.
- Runtime port tracking.
- Failed-start cleanup.

worker/__init__.py:
Package initializer. Currently empty.

The worker owns the llama-server child process.

The inference backend communicates with the running server
but does not own its process lifecycle.

LifecycleController coordinates model loading and unloading.

Server termination must release its GPU allocations.

Only one inference worker/server may be active at a time.

RESOURCE OWNERSHIP

MONITORS:
Read-only system and GPU measurements.
Never allocate memory or load models.
Never make resource-management decisions.

CORE:
Resource budgeting.
Scheduling.
Allocation decisions.
Lifecycle coordination.

MODEL CACHE:
Memory mapping.
Optional page warming.
Cache tracking.
No indiscriminate memory locking.

WORKER:
Owns the inference server subprocess.
Executes inference through the backend.
Remains active while the model is resident.
Terminates when the model is unloaded or evicted.

REGISTRY:
Tracks model identity, location and metadata.
Never loads model weights.

MANAGER:
Coordinates component startup and shutdown.
Owns component lifecycle.
Exposes application status.

9. Component Ownership and Integration
VRAMdManager

VRAMdManager is the central owner and coordinator of:

ModelRegistry
RAMCacheManager
LifecycleController
InferenceScheduler
SystemMonitor
GPUMonitor (when GPU monitoring is enabled)
ResourceBudgetCalculator
Dependency injection
VRAMdManager creates and owns ModelRegistry and RAMCacheManager.
VRAMdManager passes references to both into LifecycleController.
InferenceScheduler is owned directly by VRAMdManager.
LifecycleController does not own or recreate its dependencies.
Startup and shutdown
Application startup must not automatically load models.
Application startup must not warm model pages.
Application startup must not allocate GPU resources.
Shutdown must release all active RAM cache mappings.
Model registration only records metadata.
Current implementation status
ModelRegistry: implemented, not yet integration-tested.
RAMCacheManager: implemented, not yet integration-tested.
LifecycleController: initial implementation, not yet reviewed or tested.
InferenceScheduler: initial implementation, not yet reviewed or tested.
VRAMdManager integration: initial implementation, not yet tested.

ModelMetadataInspector:
Owned by VRAMdManager.
Uses the Python GGUF tooling bundled with the custom llama.cpp build.
Performs read-only metadata inspection.

ModelMemoryEstimator:
Owned by VRAMdManager.
Compares preliminary model memory estimates against ResourceBudget.
Does not allocate resources.

LifecycleController:
Receives ModelRegistry, RAMCacheManager and
ModelMetadataInspector through dependency injection.

Model Metadata and Memory Estimation
GGUF metadata inspection uses the Python tooling bundled with the configured custom llama.cpp build.
The configured llama.cpp installation is the authoritative source for GGUF tooling.
Metadata inspection must not load model weights into RAM or VRAM.
Tensor descriptions and storage sizes are used for preliminary memory estimates.
ModelMemoryEstimator compares estimated requirements against ResourceBudget.
CPU, hybrid and GPU execution modes are considered.
GPU-layer estimates are preliminary and proportional estimates are not guaranteed to match actual llama.cpp tensor placement.
KV cache, context buffers and backend runtime overhead must be accounted for before production loading decisions.
No memory estimate alone authorizes model loading or GPU allocation.
