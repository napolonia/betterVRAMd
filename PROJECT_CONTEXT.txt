01.1 PROJECT OVERVIEW

betterVRAMd is a self-contained Linux/WSL2 VRAM and inference resource manager.

Its purpose is to manage its own inference workloads while coordinating system RAM, GPU memory, model caching and inference processes.

The application is designed around resource safety, controlled model residency and predictable inference lifecycle management.

01.2 CORE OBJECTIVES

[01] MODEL MANAGEMENT

- Register multiple GGUF models.
- Inspect model metadata without loading weights.
- Maintain read-only model memory mappings.
- Support associated multimodal projector files.
- Track model registration and lifecycle state.

[02] RESOURCE MANAGEMENT

- Calculate safe RAM and VRAM budgets.
- Estimate model memory requirements.
- Select feasible CPU/GPU configurations.
- Allocate GPU resources when an inference model is loaded.
- Release model-owned GPU resources after unloading.
- Verify GPU memory reclamation where possible.

[03] INFERENCE MANAGEMENT

- Use a separate inference worker process.
- Maintain persistent model residency.
- Support multiple sequential inference requests.
- Support CPU-only inference.
- Support hybrid CPU/GPU inference.
- Support full GPU inference when resources permit.
- Permit only one resident inference model.
- Prevent concurrent inference workers.
- Coordinate queued requests with the active inference backend.

[04] SYSTEM STABILITY

- Prioritize resource safety over inference speed.
- Avoid unnecessary GPU workloads.
- Respect WSL2 memory limitations.
- Keep resource limits configurable.
- Avoid unnecessary model loading.
- Ensure predictable process and memory cleanup.

RESOURCE CONCEPTS AND DEFINITIONS

The following concepts must remain separate throughout the architecture.

02.1 MODEL REGISTRATION

Records model identity and metadata.

Registration includes:

- Model name and identity.
- Model file path.
- File size.
- File format.
- Registration timestamp.

Registration does not load model weights or allocate GPU memory.

02.2 MODEL CACHING

Provides read-only memory mappings of model files.

Caching may optionally include page warming.

Caching does not imply inference residency.

02.3 MODEL RESIDENCY

A model is resident when the inference backend has loaded it.

Residency may involve:

- System RAM allocations.
- GPU VRAM allocations.
- Inference runtime allocations.
- KV cache allocations.
- Computation buffers.
- Auxiliary model components.

02.4 INFERENCE ACTIVITY

Inference activity means that the backend is actively processing an inference request.

An idle inference queue does not automatically mean that the resident model must be unloaded.

Model unloading is controlled by LifecycleController and the resource-management policy.

02.5 MEMORY CONCEPTS

The following memory concepts must not be treated as interchangeable:

[01] Filesystem page cache.
[02] Explicitly pinned RAM.
[03] Memory-mapped model files.
[04] Inference runtime allocations.
[05] GPU VRAM allocations.

IMPORTANT: Memory mapping a model does not mean that its entire contents are physically resident in RAM.

mmap does not guarantee residency or protect model pages from memory pressure.

Do not indiscriminately pin model pages using mlock.

05.5 SINGLE-MODEL REQUIREMENT

Only one inference model may be loaded by the inference worker at any given time.

Multiple models may be registered.

However:

- Only one inference server may be active.
- Only one inference model may be resident in that server.
- Switching models requires unloading the previous model.
- A new model must not load while another remains resident.
- Concurrent inference workers are prohibited.
- An associated mmproj does not count as another model.

This restriction must be enforced at the manager/lifecycle coordination level.

It must not rely solely on assumptions made by the inference backend.

ARCHITECTURAL OPERATING PRINCIPLES

06.1 OBSERVE -> DECIDE -> EXECUTE

OBSERVE

Collect passive system and GPU resource measurements.

DECIDE

Calculate resource budgets, estimate model requirements and select an appropriate inference configuration.

EXECUTE

Load, unload and execute inference through the controlled inference worker.

RULE: Monitoring components must never make resource-allocation or model-lifecycle decisions.

06.2 RESOURCE MANAGEMENT BEFORE LOADING

Model loading must be preceded by resource evaluation.

The general sequence is:

[01] Observe current system and GPU resources.
[02] Calculate safe resource budgets.
[03] Inspect model metadata.
[04] Estimate model memory requirements.
[05] Select a feasible inference configuration.
[06] Check current model residency.
[07] Unload an existing model when switching.
[08] Start the inference worker.
[09] Verify server readiness.
[10] Confirm model residency where possible.

Estimates are not guarantees of successful allocation.

06.3 SINGLE ACTIVE MODEL

Only one inference model may be resident at a time.

The application must prevent overlapping model-loading operations.

Model switching requires controlled unloading before loading the replacement model.

06.4 SEPARATION OF RESPONSIBILITIES

Each component must have a clearly defined responsibility.

Components must not silently assume responsibilities belonging to other components.

Dependency ownership and process ownership must remain explicit.

RESOURCE MANAGEMENT COMPONENTS

09.1 RESOURCE BUDGET CALCULATOR

Module:

vramd/core/budget.py

Responsibility:

Calculate safe resource limits using current system and GPU measurements.

RAM budgeting considers:

- Available system RAM.
- Configured maximum RAM.
- Configured system memory reserve.

GPU budgeting considers:

- Total VRAM.
- Used VRAM.
- Available VRAM.
- Configured maximum VRAM.
- Minimum desired free VRAM.

Output:

ResourceBudget containing safe allocatable RAM and VRAM limits.

Restrictions:

- Does not allocate memory.
- Does not load models.
- Does not make lifecycle decisions.

09.2 MODEL METADATA INSPECTOR

Module:

vramd/models/metadata.py

Responsibility:

Perform read-only GGUF metadata inspection.

Requirements:

- Use Python GGUF tooling bundled with the configured custom llama.cpp installation.
- Do not load model weights.
- Do not allocate GPU memory.
- Provide model architecture information.
- Provide layer counts.
- Provide tensor descriptions and storage sizes where available.

The configured llama.cpp installation is authoritative for GGUF tooling.

09.3 MODEL MEMORY ESTIMATOR

Module:

vramd/models/estimator.py

Responsibility:

Estimate model memory requirements without allocating resources.

Current design:

- Estimate CPU-only configurations.
- Estimate GPU-only configurations.
- Estimate hybrid configurations.
- Use GGUF tensor metadata and tensor sizes.
- Account for transformer blocks.
- Account for output-layer tensors.
- Apply a 15% safety margin.
- Compare estimated requirements against ResourceBudget.

Restrictions:

- Does not load models.
- Does not allocate RAM or VRAM.
- Does not authorize model loading by itself.

Known limitations and future improvements:

[01] Include KV cache requirements based on context size.

[02] Account for computation buffers.

[03] Account for inference runtime overhead.

[04] Include multimodal projector memory where applicable.

[05] Verify GPU-layer tensor placement assumptions against supported llama.cpp architectures.

[06] Distinguish estimated feasibility from guaranteed successful model loading.

IMPORTANT: A memory estimate alone must never authorize model loading or GPU allocation.

09.4 MODEL LAYER SELECTOR

Module:

vramd/models/selector.py

Responsibility:

Select the highest feasible llama.cpp GPU-layer configuration for one model.

Design requirements:

- Evaluate CPU-only feasibility.
- Search GPU-layer configurations from highest to lowest.
- Respect max_gpu_layers.
- Do not assume feasibility is monotonic.
- Fall back to CPU-only when GPU configurations are infeasible.
- Raise NoFeasibleConfigurationError when CPU-only operation also exceeds the safe RAM budget.

Known improvements:

[01] Validate transformer block metadata explicitly.

[02] Handle incomplete GPU tensor metadata gracefully.

[03] Permit CPU-only fallback when GPU estimation fails because of incomplete metadata, provided CPU estimation is feasible.

[04] Catch only expected metadata-related estimation errors.

[05] Do not hide arbitrary programming errors.

Restrictions:

- Does not load models.
- Does not manage worker processes.
- Does not allocate GPU memory.

09.5 MODEL REGISTRY

Module:

vramd/models/registry.py

Responsibility:

Maintain model identity and registration metadata.

Tracks:

- Model name.
- Model path.
- File size.
- Format.
- Registration timestamp.

Restrictions:

- Does not load model weights.
- Does not allocate memory.
- Does not start inference workers.
- Does not make resource-allocation decisions.

Multiple GGUF models may be registered simultaneously.

09.6 RAM CACHE MANAGER

Module:

vramd/models/cache.py

Responsibility:

Manage read-only model file mappings and cache resources.

Responsibilities:

- Create read-only mmap mappings.
- Track active mappings.
- Support optional page warming.
- Clean up mappings.

Restrictions:

- Does not allocate VRAM.
- Does not load inference models.
- Does not pin all model pages indiscriminately.
- Does not start inference processes.

mmap is the default cache strategy.

Memory locking remains disabled by default.

09.7 MULTIMODAL MODEL SUPPORT

An mmproj file is an auxiliary component of its associated inference model.

Requirements:

- Must not be treated as an independent inference model.
- Must be passed to llama.cpp when required.
- Its memory requirements must eventually be included in model resource estimation.
- Must be unloaded together with its associated model.

09.8 MODEL LOADING DECISIONS

Loading decisions must account for:

- Current RAM budget.
- Current VRAM budget.
- Model metadata.
- Estimated model memory.
- GPU-layer configuration.
- Context size.
- Runtime overhead.
- Auxiliary model components.

The application must not load a new inference model while another model remains resident.

09.9 MODEL UNLOADING

Unloading must:

- Stop the associated inference worker/server.
- Release model-owned runtime resources.
- Release associated auxiliary resources.
- Clean up managed model mappings when appropriate.
- Verify GPU memory reclamation where possible.
- Report cleanup failures.

Successful process termination and successful GPU memory reclamation are separate verification conditions.

COMPONENT OWNERSHIP AND INTEGRATION

12.1 VRAMD MANAGER

Module:

vramd/core/manager.py

VRAMDManager is the central application coordinator.

It owns:

- ModelRegistry.
- RAMCacheManager.
- ModelMetadataInspector.
- ModelMemoryEstimator.
- ModelLayerSelector.
- LifecycleController.
- InferenceScheduler.
- SystemMonitor.
- GPUMonitor, when GPU monitoring is enabled.
- ResourceBudgetCalculator.

Responsibilities:

- Component construction and dependency injection.
- Application startup and shutdown.
- Resource measurement and budget calculation.
- Resource-aware model loading coordination.
- Application status reporting.
- Coordination between model lifecycle and inference scheduling.
- Single-request inference execution coordination.

VRAMDManager creates and owns ModelRegistry and RAMCacheManager.

It injects references to both into LifecycleController.

VRAMdManager remains responsible for application-level orchestration.

It obtains current resource measurements and calculates a ResourceBudget
before delegating model loading to LifecycleController.

It delegates model unloading to LifecycleController.

It owns InferenceScheduler and coordinates inference execution with
LifecycleController and the active inference backend.

The manager must not duplicate lifecycle operations or bypass
LifecycleController when obtaining or using the active backend.

Model loading decisions must use current resource measurements and a ResourceBudget before delegating model startup to LifecycleController.

Manager status reporting must obtain lifecycle information through LifecycleController.get_status(), rather than independently accessing lifecycle internal state.

The manager owns InferenceScheduler directly.

INFERENCE EXECUTION COORDINATION

VRAMDManager.execute_next() coordinates execution of one queued request.

The method:

- Requires the manager to be running.
- Retrieves the next request from InferenceScheduler.
- Checks that the requested model matches the active model.
- Obtains the active backend through LifecycleController.
- Checks backend readiness.
- Calls backend.generate() using the request parameters.
- Records successful results through InferenceScheduler.complete().
- Records execution errors through InferenceScheduler.fail().
- Returns the updated request state.

The manager does not automatically switch models when a request requires a different model.

A model mismatch is recorded as a request failure.

The execution method processes at most one request per call.

A continuous execution loop or background execution service remains separate future work.

RESOURCE-AWARE LOADING

The loading operation requires a ResourceBudget supplied by the caller.

Before caching or starting a worker, LifecycleController:

- Resolves the registered model.
- Selects the configured GPU-layer limit.
- Evaluates the model configuration using ModelLayerSelector.
- Rejects configurations that are not feasible.
- Checks existing cache and worker state.
- Creates the model mapping if necessary.
- Reserves the active-model identity.
- Starts the inference worker using the selected GPU-layer configuration.
- Verifies that the worker remains running after startup.

The returned ModelMemoryEstimate represents the selected configuration and its estimated resource requirements.

A feasible estimate does not guarantee successful inference-server allocation.

WORKER OWNERSHIP

LifecycleController coordinates WorkerProcess but does not directly create or terminate subprocesses.

WorkerProcess exclusively owns the inference subprocess.

If startup fails and the subprocess cannot be cleaned up, lifecycle state and model mapping information must be retained for safe recovery.

MODEL INSPECTION AND SELECTION

inspect_model() obtains GGUF metadata without loading model weights.

select_model_configuration() delegates configuration selection to ModelLayerSelector using the supplied ResourceBudget.

CACHE MANAGEMENT

cache_model() delegates memory mapping operations to the injected RAMCacheManager.

Only one model may be cached at a time.

Cache residency and inference residency remain separate concepts.

BACKEND ACCESS

The backend property exposes the backend associated with the lifecycle-managed worker, when available.

It does not transfer subprocess ownership to the caller.

VRAMDManager uses this property to coordinate inference execution.

MODEL UNREGISTRATION

A model must be unloaded before its registration is removed when it owns active or cached resources.

Failed resource cleanup must prevent unsafe registry removal.

STATUS REPORTING

get_status() provides an atomic snapshot of lifecycle information, including:

- Cached model count.
- Active model identity.
- Worker running state.

ARCHITECTURAL RESTRICTIONS

- Does not construct or own ModelRegistry.
- Does not construct or own RAMCacheManager.
- Does not directly create or terminate subprocesses.
- Does not independently calculate system resource budgets.
- Does not bypass resource feasibility evaluation during loading.
- Does not permit multiple resident inference models.

12.10 INFERENCE SCHEDULER

Module:

vramd/core/scheduler.py

Owned directly by VRAMDManager.

Responsibility:

Manage inference requests, scheduling order, queue state and request history.

Current functionality:

- Inference request registration.
- Request ID generation.
- Priority-based scheduling.
- FIFO ordering among requests with equal priority.
- Queue capacity enforcement.
- Request state tracking.
- Request cancellation.
- Completion and failure tracking.
- Configurable terminal request-history retention.
- Scheduler status reporting.
- Thread-safe access to shared scheduler state.
- Storage of inference generation parameters in requests.

Request generation parameters include:

- max_tokens
- temperature
- top_p
- stop
- timeout

Request states:

QUEUED
RUNNING
COMPLETED
FAILED
CANCELLED

THREAD SAFETY

The scheduler uses threading.RLock to protect shared internal state.

All public methods accessing shared scheduler state acquire the lock.

Nested locking is supported through RLock.

Internal methods that are called while the lock is already held may use unlocked helpers, such as _get_request_unlocked(), to avoid unnecessary nested locking.

REQUEST HISTORY

The scheduler retains terminal requests according to the configured scheduler_history_limit.

Eligible for pruning:

COMPLETED
FAILED
CANCELLED

Never eligible for pruning:

QUEUED
RUNNING

Request history retention must not interfere with active queue entries or running requests.

REQUEST OBJECT OWNERSHIP

The scheduler retains ownership of its internal InferenceRequest objects.

Public methods returning requests provide shallow copies:

- submit()
- next_request()
- get_request()
- list_requests()

External callers cannot directly modify internal request state through these returned objects.

Mutable fields, particularly result, may still contain shared references. Deep-copy isolation is not currently guaranteed.

EXECUTION OWNERSHIP

The scheduler manages request registration, queue ordering and request state.

It does not:

- Own an inference backend.
- Create or terminate workers.
- Load or unload models.
- Calculate resource budgets.
- Independently dispatch backend requests.

EXECUTION INTEGRATION

InferenceScheduler manages inference request state and queue ordering.

It does not own the inference backend, worker process or model lifecycle.

VRAMdManager is responsible for coordinating request execution.

Execution coordination must:

Validate requested model identity.
Ensure the requested model is the active model.
Obtain the active backend through LifecycleController.
Dispatch inference parameters to the backend.
Record successful results through scheduler completion.
Record execution errors through scheduler failure handling.
Preserve single-request and single-model execution constraints.

APPLICATION COORDINATION

VRAMdManager owns InferenceScheduler and coordinates it with
LifecycleController.

The scheduler must not independently obtain resource budgets,
select GPU configurations, load models or unload models.

Model switching and loading decisions remain under the control
of VRAMdManager and LifecycleController.

The scheduler must never bypass lifecycle-controlled resource decisions.

ERROR HANDLING AND RESOURCE CLEANUP

13.1 STARTUP FAILURES

Model startup is coordinated by LifecycleController.

Resource feasibility must be evaluated before model caching or worker startup.

If worker startup fails:

- Cleanup must be attempted through WorkerProcess.
- Process references must not be discarded when cleanup fails.
- Lifecycle state must be retained while a subprocess remains tracked.
- Model mappings must be preserved when necessary for safe cleanup.
- Cache entries created by the failed loading attempt may only be removed when worker cleanup has succeeded and no process remains tracked.
- Pre-existing cache mappings must not be removed by failed startup cleanup.

Cleanup failures must be reported without silently losing the original startup error.

A worker that remains tracked after failed startup must prevent another model from loading.

Worker termination and GPU memory reclamation remain separate verification conditions.

13.2 MEMORY CLEANUP

Failed memory mapping cleanup must be reported.

Resource cleanup failures must remain visible to the manager.

The application must distinguish successful cleanup from cleanup that was attempted but could not be verified.

13.3 INFERENCE ERRORS

The following error categories must remain distinguishable:

[01] Resource estimation errors.
[02] Model configuration errors.
[03] Worker startup failures.
[04] Backend unavailability.
[05] Inference request failures.
[06] Inference timeouts.
[07] Worker termination failures.
[08] GPU memory reclamation failures.

Inference execution errors are recorded against the corresponding scheduler request.

13.4 PROCESS TERMINATION

Shutdown should attempt graceful termination first.

Forced termination may be used according to worker policy.

Forced termination must be logged.

Shutdown failures must not silently discard process references.

13.5 GPU MEMORY RECLAMATION

Worker termination does not automatically prove that GPU memory has been reclaimed.

GPU memory measurements should be used to verify reclamation where possible.

Verification must account for unrelated GPU usage and measurement limitations.

13.6 LOGGING

Logging must provide sufficient information to diagnose:

- Resource-management decisions.
- Model lifecycle transitions.
- Worker process state.
- Inference errors.
- Memory cleanup failures.
- GPU memory reclamation.

Sensitive configuration values and API keys must not be unnecessarily exposed.

ESTABLISHED ARCHITECTURAL DECISIONS

The following decisions are established and must not be changed casually.

14.1 PROJECT IDENTITY

Project Name   : betterVRAMd
Python Package : vramd
Platform       : Linux / WSL2
Inference      : Custom CUDA-enabled llama.cpp
Model Format   : GGUF

14.2 RESOURCE MANAGEMENT

- Only one active inference model at a time.
- Only one inference worker/server at a time.
- Multiple models may be registered.
- CPU-only inference must be supported.
- Hybrid CPU/GPU inference must be supported.
- GPU inference must be supported when feasible.
- Resource budgeting must precede loading decisions.
- Memory estimates are preliminary, not guarantees.
- GPU memory reclamation must be verified where possible.

14.3 MODEL HANDLING

- Model registration does not load weights.
- Metadata inspection is read-only.
- mmap is the default cache strategy.
- Memory locking is disabled by default.
- mmproj is an auxiliary component of its associated model.
- Model switching requires unloading the previous model.
- Model mappings and inference residency are separate concepts.

14.4 INFERENCE ARCHITECTURE

- llama-server is the primary inference backend.
- The inference backend does not own the server subprocess.
- WorkerProcess exclusively owns subprocess lifecycle.
- LifecycleController coordinates model lifecycle.
- VRAMDManager coordinates application-level model loading decisions and component interactions.
- Model loading requires a current ResourceBudget.
- Model configuration feasibility must be evaluated before caching or worker startup.
- Only one inference model may be resident at a time.
- Only one inference worker/server may be active at a time.
- InferenceScheduler manages request registration, queueing, scheduling and history.
- Scheduler shared state is protected by threading.RLock.
- Terminal request history is subject to configurable retention.
- Queued and running requests must never be pruned.
- VRAMDManager coordinates single-request execution through the active backend exposed by LifecycleController.
- The scheduler does not own backend dispatch or worker lifecycle.
- The current execution interface processes at most one queued request per call.
- Continuous background execution remains future integration work.
- Requests requiring a model other than the active model must not trigger automatic model switching.
- Scheduling and execution must respect LifecycleController and resource-management decisions.
- No component may bypass single-model or single-worker enforcement.
- VRAMdManager is responsible for coordinating scheduler execution
  and backend dispatch.
- Execution integration must respect LifecycleController ownership
  and single-model/single-worker constraints.


14.5 COMPONENT OWNERSHIP

- VRAMDManager owns application-level components.
- LifecycleController receives dependencies through injection.
- WorkerProcess owns the inference subprocess.
- LlamaCppBackend owns HTTP communication.
- ModelRegistry owns registration metadata.
- RAMCacheManager owns memory mappings.
- Monitors provide measurements only.
- ResourceBudgetCalculator calculates limits.
- ModelMemoryEstimator estimates requirements.
- ModelLayerSelector recommends configurations.
- InferenceScheduler owns request state and queue management, not inference execution.

14.6 DEVELOPMENT SAFETY

- Do not run inference tests during current development.
- Avoid unnecessary GPU workloads.
- Do not recreate the working virtual environment.
- Preserve established architecture unless a justified improvement is identified.
- Prefer small, reviewable changes over unnecessary rewrites.
- Prioritize system stability over inference performance.
