PURPOSE

This document defines how betterVRAMd development is conducted.

It establishes consistent procedures for:

 - Code implementation.
 - Code review and modification.
 - Architecture preservation.
 - Testing.
 - Resource management.
 - Documentation maintenance.
 - Git operations.
 - Development handovers.
 - Collaboration between development sessions.


The objective is to maintain controlled, incremental development without introducing unnecessary complexity or resource consumption.

===============================================================================

DEVELOPMENT APPROACH
01.1 GENERAL PRINCIPLES
 [01] Implement the architecture before starting integrated testing.

 [02] Work on one logical development task at a time.

 [03] Keep implementation incremental and controlled.

 [04] Avoid unnecessary experiments and temporary implementations.

 [05] Preserve existing working code.

 [06] Prefer small, reviewable changes over unnecessary rewrites.

 [07] Avoid introducing dependencies without a clear requirement.

 [08] Prioritize implementation over lengthy explanations.

 [09] Update documentation after significant implementation
      or architectural changes.

 [10] Never assume implementation or testing has occurred
      without confirmation or supporting evidence.

01.2 DEVELOPMENT PRIORITIES

Development priorities, in order:

 1. System stability.
 2. Architectural correctness.
 3. Resource safety.
 4. Implementation completeness.
 5. Maintainability.
 6. Controlled testing.
 7. Performance optimization.


Inference speed is not the primary development objective.

01.3 DEVELOPMENT SEQUENCE

The general development sequence is:

 REVIEW
    |
    v
 PLAN
    |
    v
 IMPLEMENT
    |
    v
 REVIEW CHANGES
    |
    v
 CONFIRM IMPLEMENTATION
    |
    v
 UPDATE DOCUMENTATION
    |
    v
 CONTINUE TO NEXT TASK


Testing is conducted according to the project's testing policy.

CODING RULES
02.1 CREATING FILES

When creating a new source file:

 - Provide the complete file contents.
 - Specify the exact destination path.
 - Include required imports and dependencies.
 - Follow the established project architecture.
 - Avoid unrelated functionality.

02.2 EDITING EXISTING FILES

When modifying an existing file:

 - Check its current contents first.
 - Identify the exact changes required.
 - Prefer specific additions, removals or replacements.
 - Provide complete file replacement only when explicitly
   agreed or when it is clearly safer.

 - Specify the exact file path.
 - Preserve existing working functionality.
 - Avoid repeating unchanged code.

02.3 IMPLEMENTATION INTEGRITY
 - Never assume a file's contents without checking.
 - Never assume code was saved.
 - Never assume code was implemented without confirmation.
 - Never silently remove existing functionality.
 - Never introduce unrelated architectural changes.
 - Avoid unnecessary dependencies.
 - Keep explanations concise and technical.

02.4 PYTHON ENVIRONMENT

Project environment:

 ~/projects/betterVRAMd/.venv


Rules:

 - Preserve the existing virtual environment.
 - Never recreate it unnecessarily.
 - Avoid unnecessary package installations.
 - Preserve compatibility with the configured Python environment.
 - Use the existing custom llama.cpp installation.

02.5 IMPLEMENTATION REVIEW

Before considering a change complete:

 - Review the modified code.
 - Check imports and dependencies.
 - Check component ownership.
 - Check error handling.
 - Check resource cleanup.
 - Check compatibility with existing modules.
 - Identify remaining limitations.


Do not describe reviewed code as tested unless testing has actually been performed.

SOURCE OF TRUTH
03.1 PRIORITY OF INFORMATION

The authoritative information sources are:

 1. Current user-supplied local file contents.
 2. Confirmed local implementation changes.
 3. Current repository contents.
 4. Previous development conversations.


User-supplied current file contents take precedence.

03.2 GITHUB REPOSITORY

Repository:

 https://github.com/napolonia/betterVRAMd


GitHub is a reference, not a guaranteed representation of the latest local repository state.

IMPORTANT:

 - GitHub content may be cached or outdated.
 - Never assume the repository reflects recent local changes.
 - Never repeatedly retrieve a file when its contents appear
   outdated.
 - Request the current local file when necessary.

03.3 LOCAL CHANGE CONFIRMATION

A change being discussed or provided does not mean it has been saved locally.

Likewise:

 - Saved does not mean committed.
 - Committed does not mean pushed.
 - Pushed does not mean tested.


Never assume a commit or push has occurred without user confirmation.

03.4 HANDLING DISCREPANCIES

When repository contents differ from user-supplied contents:

 - Treat the supplied local contents as authoritative.
 - Identify the discrepancy.
 - Avoid overwriting newer local changes.
 - Request clarification only when necessary.


===============================================================================

COLLABORATION PROCEDURE
04.1 ONE TASK AT A TIME

Work on one file or logical development task at a time.

Do not combine unrelated implementation changes.

04.2 IMPLEMENTATION HANDOVER

After providing code or a modification:

 [01] Wait for the user to apply the changes.

 [02] Wait for confirmation that the changes were saved.

 [03] Review the result when necessary.

 [04] Update implementation status when appropriate.

 [05] Proceed to the next task only after confirmation.

04.3 COMMUNICATION
 - Keep responses concise and technical.
 - Avoid unnecessary explanations.
 - Do not repeat completed implementation details.
 - Do not request information already supplied.
 - Ask only for missing information that is necessary.
 - Prioritize actionable instructions and actual code.

04.4 DOCUMENTATION RENEWAL

Documentation renewal follows a separate controlled procedure.

 - Work on one documentation file at a time.
 - Preserve the information and established decisions.
 - Improve organization and readability.
 - Use plain-text ASCII-friendly formatting.
 - Avoid HTML and unnecessary document-style formatting.
 - Present documentation directly in the conversation.
 - Do not generate downloadable files unless explicitly requested.


IMPORTANT:

 Minimize unnecessary output and avoid producing multiple
 large documents in a single response.


This is particularly important for maintaining browser stability.

05.2 RESOURCE SAFETY

Development must account for limited system resources.

Rules:

 [01] Avoid unnecessary background processes.

 [02] Avoid loading large GGUF models during development.

 [03] Avoid unnecessary RAM and VRAM consumption.

 [04] Avoid unnecessary GPU-intensive operations.

 [05] Never run inference during the current implementation
      phase.

 [06] Do not perform expensive operations without justification.

 [07] Avoid actions that could freeze or destabilize Windows.

 [08] Preserve Chrome availability during development.

05.3 INFERENCE RESTRICTION

Inference testing is deferred until architecture implementation is complete.

Previous inference workloads have caused Windows system freezes.

System stability takes priority over development speed.

No inference execution is permitted during the current implementation phase.

===============================================================================

TESTING POLICY
06.1 TESTING STRATEGY

Testing is deferred until architecture implementation is sufficiently complete.

Do not run tests after every module.

Do not execute inference during implementation.

The application should be assembled before controlled integrated testing begins.

06.2 TEST CATEGORIES

Testing must distinguish between:

 UNIT TESTING

      Validates individual modules independently.

 INTEGRATION TESTING

      Validates interactions between application components.

 RESOURCE-MANAGEMENT TESTING

      Validates RAM and VRAM budgeting, allocation decisions
      and cleanup behaviour.

 GPU MONITORING TESTING

      Validates passive GPU resource measurements.

 INFERENCE TESTING

      Validates model loading, inference execution, unloading
      and GPU memory reclamation.

06.3 FINAL TESTING PROCEDURE

When architecture implementation is complete:

 [01] Review the complete application.

 [02] Identify remaining implementation limitations.

 [03] Perform appropriate unit tests.

 [04] Perform integration tests.

 [05] Validate resource-management behaviour.

 [06] Validate GPU monitoring.

 [07] Begin controlled inference testing.

 [08] Start with smaller models.

 [09] Monitor system RAM and VRAM.

 [10] Verify model unloading and GPU memory reclamation.

06.4 TESTING INTEGRITY
 - Never describe untested code as verified.
 - Never describe partially tested functionality as fully tested.
 - Record testing scope and results.
 - Record failures and corrective actions.
 - Distinguish expected behaviour from observed behaviour.


Testing must remain controlled and resource-conscious.

ARCHITECTURAL RULES
07.1 DOCUMENTED ARCHITECTURE

Respect the architectural decisions established in:

 PROJECT_CONTEXT.txt


Track implementation progress in:

 PROJECT_DEV.txt


Development procedures are maintained in:

 PROJECT_WORKFLOW.txt


Do not casually change established architectural decisions.

07.2 COMPONENT RESPONSIBILITIES

CORE:

 - Application coordination.
 - Resource budgeting.
 - Scheduling.
 - Lifecycle decisions.


MODEL LAYER:

 - Model registration.
 - GGUF metadata inspection.
 - Memory estimation.
 - GPU-layer selection.
 - RAM cache management.


INFERENCE BACKEND:

 - Backend interface.
 - Command construction.
 - HTTP communication.
 - Inference request handling.


WORKER:

 - Subprocess creation.
 - Process monitoring.
 - Process termination.


LIFECYCLE CONTROLLER:

 - Model loading coordination.
 - Model unloading coordination.
 - Model lifecycle state.


MONITORING:

 - Passive system measurements.
 - Passive GPU measurements.

07.3 OWNERSHIP RESTRICTIONS
 - Do not duplicate responsibilities between modules.
 - Prefer dependency injection where appropriate.
 - Preserve established component ownership.
 - Do not allow monitoring components to make allocation decisions.
 - Do not allow inference backends to own worker processes.
 - Do not allow the scheduler to bypass lifecycle decisions.

07.4 MODEL LIFECYCLE
 - Model registration must remain separate from model loading.
 - Registration must not load model weights.
 - Application startup must not automatically load models.
 - Application startup must not automatically warm model pages.
 - Only one inference model may be resident at a time.
 - Only one inference worker/server may be active at a time.
 - Model switching requires unloading the previous model.

07.5 RESOURCE MANAGEMENT
 - Resource budgeting must precede loading decisions.
 - Memory estimates are not guarantees of available capacity.
 - Account for KV cache and runtime overhead.
 - Respect configured RAM and VRAM limits.
 - Avoid indiscriminate memory locking.
 - Verify GPU memory reclamation where possible.

07.6 LLAMA.CPP COMPATIBILITY

Preserve compatibility with the configured custom llama.cpp build.

Installation:

 ~/llama.cpp/build-cuda/


GGUF tooling:

 ~/llama.cpp/gguf-py/


Do not casually replace the configured backend or tooling with unrelated installations.

DEVELOPMENT COMPLETION PRINCIPLES

A development task is not automatically complete because its initial implementation exists.

Before marking a task complete, establish:

 - The intended functionality has been implemented.
 - Architectural responsibilities are preserved.
 - Required integration points are addressed.
 - Known limitations are documented.
 - The implementation status is accurately recorded.


Testing status must remain separate from implementation status.

A module may be implemented but not yet tested.

A module may be reviewed but not integration-tested.

Never overstate the maturity or reliability of the application.
