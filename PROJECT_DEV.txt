MODULE: vramd/core/scheduler.py

Status : REVIEWED AREAS UPDATED — IMPLEMENTATION IMPROVEMENTS SAVED — UNTESTED

Purpose: Inference request scheduling, priority ordering and queue management.

Implemented functionality:

Request registration and validation.
Priority-based heap queue.
FIFO ordering for equal priorities.
Explicit request lifecycle states.
Request completion, failure and cancellation.
Configurable terminal history retention.
Automatic pruning of oldest terminal requests.
Protection of queued and running requests during pruning.
Thread-safe access using threading.RLock.
Single-running-request enforcement.
Safe handling of stale queue entries.
Shallow-copy snapshots through get_request() and list_requests().
Internal request retrieval through _get_request_unlocked().
Scheduler statistics through get_status().
Priority type validation.
Generation parameter storage and validation.
Validation of max_tokens, temperature, top_p and timeout.
Stop sequence validation and normalization into immutable tuples.

Recent corrections:

complete() and fail() return shallow copies of terminal requests
before history pruning.
This allows VRAMDManager.execute_next() to return the request result
even when scheduler_history_limit is zero.
A zero history limit therefore removes terminal requests from
scheduler storage without preventing the caller from receiving
the completed or failed request.

Known limitations:

Mutable nested fields such as result remain shared references
in shallow copies.
Scheduler execution is coordinated externally by VRAMDManager.
The complete scheduler dispatch path has not been tested.
Direct InferenceRequest construction can bypass submit() validation.

All changes are saved locally but remain untested.

=============================================================================== CURRENT INFERENCE ARCHITECTURE

02.1 PRIMARY BACKEND

Primary Backend : llama-server Optional Backend : llama-cli (Future)

llama-server is the primary inference backend.

02.2 COMPONENT OWNERSHIP

VRAMdManager:

Central application coordinator.

Owns and coordinates application-level components.

LifecycleController:

Coordinates model registration, residency, loading and unloading.

WorkerProcess:

Owns llama-server subprocess creation, monitoring and termination.

LlamaCppBackend:

Communicates with the running llama-server through HTTP.

RAMCacheManager:

Manages model file memory mappings.

ModelRegistry:

Manages registered model identities.

InferenceScheduler:

Manages inference request ordering, queueing and request states.

ResourceBudgetCalculator:

Calculates available RAM and VRAM budgets.

ModelLayerSelector:

Selects feasible CPU/GPU configurations using model estimates and current resource budgets.

02.3 LIFECYCLE AND LOADING FLOW

The intended model loading sequence is:

[01] VRAMdManager receives a model loading request.

[02] VRAMdManager obtains current system and GPU measurements.

[03] ResourceBudgetCalculator calculates the current budget.

[04] LifecycleController retrieves model information.

[05] ModelMetadataInspector provides model metadata.

[06] ModelMemoryEstimator estimates model requirements.

[07] ModelLayerSelector selects a feasible configuration.

[08] LifecycleController validates feasibility.

[09] RAMCacheManager creates the model mapping.

[10] WorkerProcess starts llama-server.

[11] WorkerProcess verifies server readiness.

[12] LifecycleController records the successful active model.

[13] VRAMdManager reports the resulting model status.

This is the intended architecture.

The complete manager-level orchestration path has not yet been implemented.

02.4 UNLOADING FLOW

The intended unloading sequence is:

[01] VRAMdManager receives an unloading request.

[02] LifecycleController validates the requested model.

[03] WorkerProcess stops the inference server.

[04] Successful process termination is established.

[05] LifecycleController releases the model mapping.

[06] Cache and model residency states are updated.

[07] VRAMdManager reports the resulting status.

GPU memory reclamation must be treated separately from successful subprocess termination.

02.5 ARCHITECTURAL RESTRICTIONS

Only one inference worker/server may be active at a time.
Only one inference model may be resident at a time.
The backend communicates with the running server.
WorkerProcess owns the server subprocess.
LifecycleController coordinates model lifecycle.
VRAMdManager coordinates application-level components.
InferenceScheduler must respect lifecycle decisions.
The scheduler must not independently load or switch models.
No component may bypass lifecycle-controlled resource decisions.

Worker and backend integration has not been fully validated.
